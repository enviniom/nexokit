# HTTP Middleware Specification

## Purpose
Define the middleware stack: RequestID, Recovery, CORS, and Logger, including execution order.

## Requirements

### Requirement: RequestID middleware

The system MUST generate a UUID request ID when the `X-Request-ID` header is absent and propagate it to the response header.

#### Scenario: Missing request ID

- GIVEN a request without `X-Request-ID`
- WHEN it passes through the middleware
- THEN the response contains `X-Request-ID` with a generated UUID

#### Scenario: Existing request ID

- GIVEN a request with `X-Request-ID: abc-123`
- WHEN it passes through the middleware
- THEN the response contains `X-Request-ID: abc-123`

### Requirement: Recovery middleware

The system MUST recover from panics in handlers, write HTTP 500 with the standard error envelope, and push the panic value into `gin.Context.Errors` so `ErrorLogger` owns the log line. `Recovery` MUST NOT emit its own `slog.Error` record. (Previously: `Recovery` recovered panics, wrote 500, and logged panic details itself; now logging is delegated to `ErrorLogger` and panic information is attached to `c.Errors` for unified handling.)

#### Scenario: Handler panic

- GIVEN a handler that calls `panic("boom")`
- WHEN a request hits that handler
- THEN the client receives 500
- AND the standard envelope shows `success: false`
- AND the server process remains alive
- AND `c.Errors` contains the panic value for the new `ErrorLogger`

#### Scenario: Recovery does not log

- GIVEN a handler that panics
- WHEN the request is processed
- THEN only `ErrorLogger` emits the error log line, not `Recovery`

### Requirement: CORS middleware

The system MUST enforce CORS policy using `CORS_ALLOWED_ORIGINS` from config.

#### Scenario: Allowed origin

- GIVEN `CORS_ALLOWED_ORIGINS=http://localhost:3000`
- WHEN a preflight request arrives from `http://localhost:3000`
- THEN CORS headers are present and the request is allowed

#### Scenario: Disallowed origin

- GIVEN `CORS_ALLOWED_ORIGINS=http://localhost:3000`
- WHEN a request arrives from `http://evil.com`
- THEN CORS headers deny the origin

### Requirement: Logger middleware

The system MUST log every request with method, path, status code, duration, and request ID.

#### Scenario: Successful request

- GIVEN a GET request to `/health`
- WHEN it completes with 200
- THEN the log line contains `method=GET`, `path=/health`, `status=200`, `duration>0`, and `request_id`

### Requirement: Message constants

Middleware MUST use `internal/platform/messages/` constants for project-owned string values. Standard HTTP header names MAY remain literals.

#### Scenario: Compile and vet pass after constant migration

- GIVEN `messages.go` exports `MsgHTTPRequest`, `CtxRequestID`, `HeaderRequestID`, and CORS value constants
- AND middleware files and `logger_test.go` reference those constants
- WHEN `go vet ./...` runs
- THEN exit code is 0

### Requirement: Middleware order

The system MUST register middleware in this order: `RequestID → Logger → ErrorLogger → Recovery → CORS → RateLimit` (when enabled). Gin unwinds middleware in reverse-registration order, so each post-`c.Next()` body runs after every inner middleware/handler. `ErrorLogger` is a post-`c.Next()` middleware that iterates `c.Errors`; it MUST be registered BEFORE `Recovery` so its body runs AFTER `Recovery`'s `defer recover()` and `c.Error(panicValue)` call. `RequestID` MUST remain outermost so `request_id` is on the context for every later middleware. (Previously: `RequestID → Logger → Recovery → CORS → RateLimit`; `ErrorLogger` is now inserted between `Logger` and `Recovery` so panics and handled errors share one log path under `ErrorLogger`.)

#### Scenario: Panic with request ID

- GIVEN a handler that panics
- WHEN the request is processed
- THEN the `ErrorLogger` log line includes the same `request_id` generated by RequestID middleware

#### Scenario: ErrorLogger observes panic after Recovery unwinds

- GIVEN the chain `RequestID → Logger → ErrorLogger → Recovery → CORS`
- WHEN a handler panics
- THEN `Recovery` recovers, writes 500, and pushes the panic value into `c.Errors`
- AND `ErrorLogger`'s post-`c.Next()` body runs AFTER `Recovery` returns
- AND exactly one `ErrorLogger` log line is emitted containing the panic value in the internal error chain

#### Scenario: ErrorLogger observes handled AppError

- GIVEN the chain `RequestID → Logger → ErrorLogger → Recovery → CORS`
- WHEN a handler returns an `*AppError` and `response.HandleError` writes the response and calls `c.Error(err)`
- THEN on the unwind, `ErrorLogger` emits one log line with the AppError's `code` and `public_message`

#### Scenario: Rate limit applied after CORS

- GIVEN a request exceeds the rate limit
- WHEN it passes through the middleware stack
- THEN CORS headers are set before the 429 response is returned

### Requirement: Rate limit middleware

The system MUST support a rate limit middleware that can be selectively applied to routes. When active, it extracts the client IP, checks the rate limiter, and returns HTTP 429 when exceeded.

#### Scenario: Rate limit middleware on login route

- GIVEN rate limiting is enabled and configured
- WHEN a POST to `/api/v1/auth/login` exceeds the login rate limit
- THEN the middleware returns HTTP 429 before the handler executes

#### Scenario: Rate limit middleware bypassed when disabled

- GIVEN `RATE_LIMIT_ENABLED=false`
- WHEN any request passes through the middleware
- THEN the middleware calls the next handler without checking limits

### Requirement: ErrorLogger middleware

The system MUST expose `middleware.ErrorLogger(log *slog.Logger) gin.HandlerFunc` that runs after `c.Next()`, iterates `c.Errors`, and emits one `slog.LevelError` record per error. Each record MUST include `request_id`, `method`, `path`, `status`, `latency_ms`, `tenant_id`, `actor_id`, `code`, `public_message`, and the full unwrap chain of the internal error. The logger MUST read `request_id` from the key set by `RequestID`. The router MUST wire an injected logger (production: `infra/logger.NewErrorLogger`).

#### Scenario: Handled error produces one log line

- GIVEN a handler returns `apperror.Internal(code, "boom", errors.New("kaboom"))`
- WHEN the request completes
- THEN exactly one `slog.Error` is emitted with `request_id`, `method`, `path`, `status=500`, `code`, and `internal_chain="kaboom"`

#### Scenario: Panic produces one log line

- GIVEN a handler panics with `panic("boom")`
- WHEN the request completes
- THEN exactly one `slog.Error` is emitted by `ErrorLogger` containing the panic value in the internal error chain

#### Scenario: tenant_id and actor_id present when set

- GIVEN the authenticated user and tenant are on the gin context
- WHEN the request completes with an error
- THEN the log record contains `tenant_id` and `actor_id` from the context

#### Scenario: Missing context fields are empty strings

- GIVEN a request without an authenticated user or tenant
- WHEN the request completes with an error
- THEN the log record contains `tenant_id=""` and `actor_id=""`

## Constraints and Edge Cases

- `ErrorLogger` MUST be registered before `Recovery` so its post-`c.Next()` body runs after `Recovery` attaches panic errors.
- `Recovery` MUST NOT emit its own log lines.
- Recovery MUST catch panics in middleware that runs after it (in reverse registration order).
- Logger MUST NOT leak request bodies or query parameters containing passwords.
- CORS MUST handle preflight (`OPTIONS`) requests correctly.
